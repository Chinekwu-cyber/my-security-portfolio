Generating separate RSA key pairs for a two party exchange

Set up two independent key environments so that each party in a message exchange holds its own private key, and confirmed the structure of the generated material.

what I did

  • Created an isolated working directory for each party so that key material for one could never be read from the other's folder.
  • Generated 2048 bit RSA private keys with openssl genrsa and confirmed the public exponent came out as 65537, the standard choice.
  • Listed and opened the PEM file to see the encoded private key, which made the point concrete: this file is the secret, and it never leaves its owner.
  • Hit a failed lookup from a typo in the filename, which taught me to verify a key file exists before assuming a generation step worked.

commands

$ mkdir MESSI && cd MESSI $ openssl genrsa -out keypairMESSI.pem 2048 $ ls keypairMESSI.pem $ cat keypairMESSI.pem
Why it matters: key separation is the first control in any PKI. If both parties share a directory or a key, non repudiation is gone before the first message is sent.

Pulling a live TLS certificate and walking the trust chain

Retrieved the certificate chain served by a public host on port 443 and read the trust path from the leaf certificate up to the root authority.

what I did

  • Probed the host with telnet first and got a refused connection, which confirmed the service does not answer in clear text and needs a TLS client.
  • Connected with openssl s_client on port 443 and saved the certificate to a local PEM file.
  • Read the verification output at each depth: the root authority at depth 2, the intermediate issuing CA at depth 1, and the leaf certificate at depth 0 naming the organisation and its location.
  • Confirmed every depth returned a verify result of 1, then opened the base64 body of the saved certificate.

commands

$ echo -n | openssl s_client -connect example.com:443 \ | sed -ne '/BEGIN CERT/,/END CERT/p' > ./site.pem $ cat site.pem
Why it matters: reading a chain by hand is how you tell a healthy certificate from an expired, self signed or wrongly issued one during an incident, instead of trusting a padlock icon.

Encrypting and recovering a sensitive file with AES-256-CBC

Took a file holding a mock account reference, protected it at rest with a passphrase derived key, then proved the round trip by recovering the exact original text.

what I did

  • Wrote a small plaintext file standing in for a record that must not sit readable on disk.
  • Encrypted it with AES-256-CBC, base64 armour for safe transport, and 10,000 key derivation iterations to slow down offline guessing.
  • Debugged two failed runs caused by a mistyped derivation flag, read the manual page, and corrected the syntax rather than dropping the protection.
  • Displayed the ciphertext to confirm the content was unreadable, then decrypted with the matching cipher, iteration count and passphrase and compared the result with the original.

commands

$ openssl enc -aes-256-cbc -in urgent -out ENCurgent \ -base64 -iter 10000 -pbkdf2 $ cat ENCurgent $ openssl enc -aes-256-cbc -in ENCurgent -out plain -d \ -base64 -iter 10000 -pbkdf2
Why it matters: encryption at rest is only reversible if the cipher, the derivation function and the iteration count are recorded. Lose any of those and the data is gone, which is a real recovery risk, not a theory.

Fingerprinting a file and preparing a signing key

Built the two halves of a digital signature workflow: a hash that fingerprints the content, and a signer key pair that binds that fingerprint to an identity.

what I did

  • Created a data file and produced a message digest for it, giving a fixed length fingerprint of the exact bytes.
  • Generated the signer's 2048 bit RSA key pair in a dedicated signing workspace.
  • Repeated the digest after changing the file to see the fingerprint change completely, which is the property the whole scheme rests on.
  • Noted that MD5 is fine for a teaching lab but is not collision resistant, so production integrity checks belong on SHA-256 or stronger.

commands

$ echo "This is my secret key 22336" > someData.txt $ md5sum someData.txt $ openssl genrsa -out keypairBOB.pem 2048 $ sha256sum someData.txt # production equivalent
Why it matters: a signature is a hash encrypted with a private key. Understanding both halves is what lets an analyst say whether a file has been altered in transit or is genuinely from who it claims.

  • ICMP

Mapping live hosts on a lab subnet at layer 2 and layer 3

Swept a small lab subnet for reachable hosts, then used the ARP cache to separate hosts that are genuinely absent from hosts that are simply refusing to answer.

what I did

  • Ran an ICMP sweep against a target address and recorded 100 percent packet loss with destination host unreachable returned by the gateway.
  • Read the local ARP cache to map every IP on the segment to its hardware address on the interface.
  • Found one address sitting at incomplete, meaning no device answered the address resolution request, while two others resolved to real hardware addresses.
  • Concluded that a silent host is not proof of an empty address, because filtering and resolution failure look different at layer 2.

commands

$ ping 172.20.10.2 $ arp -a
Why it matters: the same ARP table that maps a network is the place a defender spots two addresses claiming one hardware address, which is the signature of ARP spoofing on the segment.

Measuring how fast a short archive passphrase falls

Ran a controlled recovery exercise against a training archive supplied with the lab, to put a number on the advice that short passwords are unsafe.

what I did

  • Confirmed the archive encryption method in use before choosing an approach.
  • Ran a brute force search across a one to four character key space against the lab archive and recovered the passphrase.
  • Recorded the failed run against a file that did not exist, a reminder to verify the target path before reporting a negative result.
  • Translated the outcome into policy language: minimum length, character variety, and why archive passwords should never be the reusable ones.

commands

$ fcrackzip -v -u -l 1-4 file-2.zip
Why it matters: a policy line like "use twelve characters" persuades nobody. Showing that a four character passphrase falls in seconds inside a lab does, and that is the argument an awareness session needs. Run only on data I was authorised to test.
Artefact analysis
  • Kali Linux VM
  • xxd
  • file headers

Catching a file that lies about its own type

Triaged a suspicious image inside an isolated virtual machine by reading its header bytes instead of trusting the extension, and found the two did not agree.

what I did

  • Staged the sample in a dedicated folder inside a VM with no production access, alongside a known web shell sample from a training kit, so that handling suspicious artefacts stayed contained.
  • Dumped the first bytes of the file and read the magic number, which identified a RIFF WEBP container despite the .jpeg extension on the file name.
  • Confirmed the mismatch by attempting to open the file and watching the viewer report an unsupported feature rather than rendering cleanly.
  • Wrote up the finding as a triage rule: extension is a label, the header is the evidence.

commands

$ xxd cat.jpeg | head -n 2 00000000: 5249 4646 ... 5745 4250 RIFF....WEBP $ file cat.jpeg
Why it matters: renaming a payload to look like a harmless image is one of the oldest delivery tricks there is. Header checks are a fast first step in any attachment triage queue.
